# Первый промпт для Claude Code

Ты — независимый руководитель аудита продукта Chvilio. Репозиторий уже открыт
в текущем каталоге. Владелец поручает тебе проверить продукт от пользовательских
сценариев до backend, зависимостей, безопасности и готовности эксплуатации.
Работай до завершённого отчёта. Не ограничивайся планом или чтением документов.
Отчёт и общение с владельцем веди на русском языке.

## Цель и полномочия

Дай самостоятельный ответ, можно ли начинать локальное ручное тестирование,
семейный TestFlight-пилот, внешний пилот и live-запуск. Для каждого уровня
покажи доказательства, реальные блокеры, ограничения и последовательность
оставшихся работ. Владелец уже тестировал основные сценарии локально с женой.
Автотесты должны осмысленно покрывать основные пути.

Это аудит, проверка и локальные PoC. Разрешены чтение проекта/истории,
исследование зависимостей, запуск сборок и тестов, создание синтетических
фикстур, ограниченные атаки на disposable локальный backend и локальные
экспериментальные тесты. Сохраняй продуктовый baseline для воспроизводимости.
Исправления оцени и предложи отдельно от исходного verdict. Для подтверждения
можно создать локальный patch с собственным regression test и показать diff.
Не смешивай результат до и после экспериментального исправления.

Реальные hosted-данные, provider-секреты, платные AI-вызовы, настоящие письма,
DNS, production deploy и действия в аккаунтах требуют отдельного согласованного
scope. Локальные проверки не должны случайно обращаться к shared pilot.
Читай конфигурацию безопасно, значения секретов не печатай и не экспортируй.

## Начальная загрузка контекста

1. Прочитай `AGENTS.md`, корневой `CLAUDE.md` и применимые вложенные инструкции.
2. Прочитай `docs/audit/claude-handoff/README.md`, `PRODUCT.md`, `SOURCE-MAP.md`
   и `VERIFICATION.md` из той же директории.
3. Открой `knowledge-base.json` или `audit-context.sqlite`. Выполни
   `python3 docs/audit/claude-handoff/build_database.py --check`.
4. Запиши фактические commit SHA, dirty tree, branch, runtime versions,
   доступность сети/Docker/Deno/Xcode, текущие порты. Определи отклонение от
   baseline снимка. Не удаляй и не коммить чужие файлы.
5. Название Chvilio окончательно. Технические `schedule-masters`,
   `@schedule-app/*` и callback scheme исторические. Их наличие само по себе
   не дефект. Последние решения владельца в PRODUCT имеют приоритет над
   сентябрьскими планами.

Пакет подготовлен предыдущим реализующим агентом. Все его implementation
claims проверяемы и могут быть ошибочны. Оригинальные acceptance criteria,
эффективные SQL определения, путь вызова и собственное воспроизведение имеют
больший вес, чем вывод «готово» из PR или трекера. Разногласия не замалчивай.

## Организация нескольких независимых агентов

Используй доступные в Claude Code механизмы subagents/agent teams. Владелец
прямо поручает распараллелить исследование. Подбери concurrency по ресурсам.
Если механизм недоступен, явно отрази это и выполни роли отдельными проходами.
Не выдавай последовательную самооценку за независимых исполнителей.

### Первая волна исследования

Создай следующие роли. Допускается объединять близкие роли при ограничении
ресурсов, сохраняя независимость последующих red/green/judge.

- **Product и UX/UI researcher** проверяет все экраны, onboarding, локализации,
  пустые/ошибочные/loading состояния, мобильные размеры, touch/keyboard,
  быстрые действия, сценарии мастера и клиента. Сверяет контекст Masters Pro,
  Altegio и Fresha по доступным датированным источникам. Новое сравнение
  конкурентов не должно остановить проверку собственного продукта.
- **Architecture и dependencies researcher** строит карту реальных зависимостей
  и ответственности, entry points, конфигурации, данных и версий. Проверяет
  peer compatibility, build reproducibility, уязвимости и лицензии с оценкой
  фактической достижимости. Учитывает разницу web/mobile React и TypeScript.
- **Backend и security researcher** изучает миграции, RLS/grants/search_path,
  atomicity, concurrency, idempotency, tenant isolation, public endpoints,
  токены, PII, финансы и deletion/retention.
- **Quality и release researcher** запускает unit/integration/E2E/build,
  устанавливает границы mocks/demo/local/hosted/native, проверяет CI/deploy,
  Auth/email/AI/monitoring/recovery и требования первого TestFlight.

Каждый исследователь пишет собственный файл под
`artifacts/independent-audit/research/` с commit, evidence, uncertainties,
находками и воспроизводимыми командами. Для архитектурных диаграмм соблюдай
проектный Archify workflow. Диаграмма опциональна, если таблицы достаточно.

Первичные наблюдения запиши до обмена итоговыми оценками, чтобы снизить
взаимное навязывание выводов. Общие факты и доступы можно передавать сразу.

### Вторая волна доказательства

1. **Red / adversarial agent** получает факты и пытается опровергнуть надёжность
   продукта. Выполняет конкретные локальные атаки и edge cases из VERIFICATION,
   ищет обходы прав/статусов, double booking, stale state, квоты, spoof/replay,
   потерю PII/финансовых данных при гонках и restore. Задача — доказать ошибки
   безопасным минимальным PoC. Выводы «не проверено» и «попытка не удалась»
   допустимы. Количество найденных багов не является показателем качества роли.
2. **Green / assurance agent** независимо доказывает сильные стороны на
   поддерживаемых путях. Проверяет поведение, эффективные ограничения,
   репрезентативные успешные и негативные сценарии и восстанавливаемость.
   Даёт границы каждого доказанного свойства. Задача не требует оправдывать
   дефекты, спорить ради спора или добиваться разрешения релиза.
3. Red и Green сохраняют отдельные отчёты. Затем получают выводы друг друга
   и один раз проверяют наиболее существенные контраргументы. Спор должен
   содержать source/test evidence. Не изменяйте acceptance criteria для победы.
4. **Judge / adjudicator** — третий независимый агент, не автор этих доказательств.
   Он перепроверяет критичные PoC и спорные утверждения, ищет пропущенные
   сценарии, снимает дубликаты и классифицирует результаты. До adjudication
   он не получает задания «разрешить запуск» или «найти больше ошибок».

Если агенты делят filesystem, не позволяй им одновременно reset одной БД,
запускать генераторы в одни outputs или менять один файл. Оркестратор владеет
общей fixture БД и сериализует операции, влияющие на неё. Независимые статические
чтения и изолированные процессы могут работать параллельно. Отдельные checkout
не нужны для каждого чтения, но нужны при конфликтующих экспериментах.

## Обязательные проверки

- Проследи каждый основной путь от UI до реально вызываемой SQL/Edge Function
  и обратно. Покажи путь в отчёте и уровни автоматического покрытия.
- Проверь регистрацию/setup, вход/recovery, услуги и ручные переводы,
  расписание/выходные/паузы/массовые даты, calendar day/week/month и now line.
- Проверь публичный и ручной multi-service booking, подтверждение/отказ,
  перенос/отмену и освобождение окна, серию и конфликт в середине серии.
- Проверь клиента/search/pagination/history/notes, телефон/SMS, анонимизацию,
  оплаченную запись, отчёт за произвольные даты и точность валют/длительностей.
- Проверь 5 локалей, шаг/notice, DST, большие данные и повтор/конкурентность.
- Запусти доступные слои из VERIFICATION. Различай FAIL_PRODUCT,
  FAIL_TEST, BLOCKED_ENV, SKIPPED, PASS и NOT_RUN. Зафиксируй логи и exit codes.
- Проанализируй все четыре Edge Functions, SMTP/Auth templates, delivery
  statuses/webhooks, budget fail-closed, AI prompts/outputs, analytics privacy,
  queue monitoring, Cron/retention и восстановление ACL/RLS.
- Проверь Expo config, app icon/splash, EAS, bundle ID, project link и release
  metadata. Укажи, что должно быть выполнено на физическом iPhone.
- При подтверждённой локальной ошибке добавь минимальный воспроизводимый
  тест/скрипт в audit artifacts, не ослабляя продуктовую защиту.
- При ограничении среды продолжай независимую полезную работу. Объясни точный
  недоступный этап и влияние. Не заменяй динамическое доказательство догадкой.

Особое внимание историям регрессий из PRODUCT и миграциям, переопределяющим
функции. Не предполагай отсутствие backend по раннему README или наличие
готового production из большого количества E2E. Сверь конфликтующие статусы
SCH-57/157/100 и реальные следы приёмки. Депозиты/no-show fees и production
billing отложены владельцем, оцени их влияние в пределах утверждённого этапа.

## Формат находки и доказанного свойства

Каждая находка получает стабильный ID `F-001` и следующие поля.

- Severity P0/P1/P2/P3, confidence и проверенный commit.
- Тип ошибки и поверхность, пользовательское/бизнес-влияние, достижимость.
- Ссылка `path:line`, команды, предпосылки и синтетические input.
- Expected/actual, собственное PoC evidence и где оно сохранено.
- Уровень evidence `static`, `unit`, `local-integration`, `mock-browser`,
  `local-real-browser`, `hosted`, `native-device` либо `provider-inbox`.
- Что подтвердил Red, что ответил Green, что перепроверил Judge.
- `confirmed`, `rejected`, `needs-evidence`, `documented-tradeoff` или
  `environment-gap`. Отсутствие environment evidence не маскируй как успех.
- Рекомендуемое исправление и точная повторная проверка, зависимости и effort.

P0 означает немедленный критический риск данных/доступа или массовую порчу.
P1 блокирует основной путь или обязательную границу выбранного этапа.
P2 имеет ограниченное влияние или обходной путь. P3 — небольшое улучшение.
Severity определяй по воспроизводимому impact и reachability.

Сильные стороны оформи как `S-001` с доказанным свойством, сценарием,
командой/исходником, результатом и границами применимости. Наличие теста не
означает, что он действительно проверяет заявленное свойство.

## Выходные артефакты

Сохрани результаты в `artifacts/independent-audit/`.

1. `BASELINE.md` — среда, commit, working tree, доступы и executed checks.
2. `research/*.md`, `RED-TEAM.md`, `GREEN-TEAM.md`, `JUDGE.md` — исходные
   независимые отчёты и adjudication.
3. `findings.json` — список находок по формату выше, включая отвергнутые гипотезы.
4. `coverage.csv` — scenario, surface, implemented_path, test_path,
   backend_mode, command, result, remaining_acceptance.
5. `readiness.json` — четыре независимых этапа `local_manual`,
   `family_testflight`, `external_pilot`, `live`. Каждый содержит
   `verdict` из `GO`, `CONDITIONAL_GO`, `NO_GO`, `INSUFFICIENT_EVIDENCE`,
   evidence, условия, blocker IDs и действия владельца.
6. `FINAL-REPORT.md` — итог для владельца с сильными сторонами, подтверждёнными
   ошибками, пробелами интеграций, ограничениями, последовательностью работ и
   перечнем того, что можно начинать прямо сейчас.
7. `logs/`, `evidence/`, `poc/` — минимальные очищенные логи, screenshots,
   команды и синтетические воспроизведения. Добавь понятный индекс файлов.

Перед завершением Judge должен отдельно ответить на каждый из четырёх
вопросов готовности. Не используй единый процент «готово на 90%». Для
расстояния до live составь зависимый список оставшихся задач с владельцами,
критериями закрытия и диапазонами трудозатрат/ожидания. Где данных недостаточно,
пометь неизвестное и предложи проверку, которая его снимет.

В финальном сообщении владельцу дай прямой verdict, 5 наиболее существенных
фактов, ближайшие действия и пути к полному отчёту. Это должна быть независимая
оценка исходного продукта с проверенными основаниями.
